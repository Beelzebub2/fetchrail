# Fetchrail local reliability build

This branch integrates upstream `fddef19` (Fetchrail 0.5.3, including release automation) with the local reliability work in `9276416`. The application is `0.6.3-local.9` and the companion is `0.6.3`. It keeps the existing installation and profile identity. Do not publish this as an upstream release.

The local.9 range scheduler reports the connection target without waiting for the download record lock. Its range futures are polled by this same scheduler; awaiting a fair lock behind a queued worker can stop both permanently. A busy display update waits until the next sample while transfers continue. The regression test queues a worker behind the record lock, demonstrates the blocking parent acquisition, then checks worker completion and the subsequent connection update. Request counts, durable checkpoints and publication checks retain their existing behavior. See [Tokio's fair lock policy](https://docs.rs/tokio/latest/tokio/sync/struct.RwLock.html) and [FuturesUnordered polling requirements](https://docs.rs/futures-util/latest/futures_util/stream/struct.FuturesUnordered.html). A detailed local trace exposed this failure; it does not establish that earlier remote-host speed dips had the same cause.

New direct-write staging files use sparse allocation on supported Windows volumes, avoiding physical zero-fill before high-offset writes. Unwritten regions still read as zeros; unsupported volumes retain ordinary allocation, and existing partial files retain their layout. Free-space checks, durable range hashes, full-file checksum verification and Windows attachment checks remain in place. See [Microsoft's sparse-file operations](https://learn.microsoft.com/en-us/windows/win32/fileio/sparse-file-operations).

Sparse staging allocates physical space as data arrives rather than reserving the full file upfront. Concurrent downloads or other programs can fill the disk after the initial check; write errors still prevent publication, and space must be freed before resuming.

Durable JSON creation, writing, syncing and metadata replacement run together on the blocking pool, so a slow Windows metadata move cannot block the async task polling the range workers. Backup-before-primary ordering is retained. Destination collision checks also use asynchronous metadata operations; final publication still refuses to overwrite existing files. See [Tokio's filesystem guidance](https://docs.rs/tokio/1.53.1/tokio/fs/index.html).

Full-file SHA-256 verification batches sequential reads and hashing in one blocking task, using an 8 MiB buffer and the Windows sequential-scan hint. It still runs after attachment processing, which may alter a file. Pause/cancel checks run between chunks; finalization waits for the hash worker to release its handle before returning, preventing a detached verifier from racing cleanup or resume. The transfer scheduler, request ceiling and five-second durable checkpoint cadence remain unchanged. See [Tokio file I/O tuning](https://docs.rs/tokio/1.53.1/tokio/fs/index.html#tuning-your-file-io) and [blocking-task cancellation](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html).

The upstream interface, progress windows, completion options, batch browsing, per-file/global byte-per-second limits, queue start/stop windows and Chrome Web Store host support are retained. Durable checkpoints, direct staging, no-replace publication and idempotent browser handoff keep the local implementation. Existing settings survive migration; the new upstream settings use safe defaults. If both the existing KiB/s limit and new byte-per-second limit are configured, both apply. Browser credentials remain session-only: after desktop restart, refresh the link/session before resuming an authenticated download.

The HTTP engine uses a fresh range GET, strong ETag checks and identity encoding. Every resumable range has a durable byte count and SHA-256 checkpoint. A supplied trusted SHA-256 is checked before publication. An unverified or changing representation is rejected or uses one stream. Refreshed URLs can retain bytes only with the original trusted digest or the same resource's strong validator; otherwise select Restart. Uncapped requests compare recent ten-second progress windows: after thirty seconds, a request below 2 KiB/s or 5% of its best window retries only its missing suffix using a fresh transport pool, which is then retained by that worker. A fast prefix cannot hide a trickling tail. The final remaining request also compares against sustained per-request speed proven by two consecutive uncontended four-second windows with at least four receiving requests in this same download; this catches a straggler slow from its first byte. Configured bandwidth limits bypass the detector, shared-origin waits suspend the peer comparison, and a uniformly slow download establishes its own low reference.

The local.8 lockfile advances only the HTTP/2 implementation from h2 0.4.19 to 0.4.20, retaining the existing resolution of other dependencies. It includes the upstream fix for automatic DATA-frame budgets after adaptive receive-window changes, which could otherwise reset valid streams. Protocol negotiation and reusable worker pools remain enabled; short host probes do not establish a universal HTTP/1.1 or HTTP/2 speed winner. See [the reviewed h2 correction](https://github.com/hyperium/h2/pull/965), [reqwest's adaptive-window API](https://docs.rs/reqwest/0.13.5/reqwest/struct.ClientBuilder.html#method.http2_adaptive_window), and [AWS's guidance on fresh connections for slow-request retries](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html#timeouts-and-retries). AWS's guidance informs the recovery strategy; it does not identify a download host's backend. The native fixture now includes a final range that trickles from its first byte alongside faster peers, and requires a verified suffix retry and exact full-file SHA-256. Detailed profiling binaries and captures stay in ignored artifacts.

Workers share a queue of ranges independent of the worker count. Large files use pieces up to 32 MiB with enough queued work for every worker, reducing request overhead; existing resume ledgers keep their original layout. Each parallel worker owns a reusable transport pool, preserving HTTP/1.1 and HTTP/2 negotiation while avoiding one shared HTTP/2 transport bottleneck. Browser-session clients use the same transport settings and retain their credential redirect boundary. Adaptive mode starts with up to four simultaneous requests, averages two four-second throughput samples, and tests higher counts for useful gains or lower counts for comparable speed. Once fewer requests prove slower, it retains the faster count instead of repeatedly sacrificing throughput. A stable-window bandwidth change of more than 20% or server throttling allows lower counts to be tested again; higher counts are periodically reconsidered where capacity remains. All jobs share FIFO per-origin request admission, Retry-After cooldowns and the optional global KiB/s limit. Shared-budget waits are excluded from connection-count comparisons. Network permits are released before checkpoint work, so one file's disk sync does not occupy another file's request allowance. Interrupted bodies retry their remaining bytes. Exhausted transient failures wait and retry automatically; pause/cancel remain available.

Progress bars represent compact file sections, which can contain multiple receiving requests. The main list, throughput summary and progress window report the actual receiving connection count separately from the worker target. Waiting sections are labeled Waiting, and paused downloads report no receiving connections. This desktop-only update uses the existing signed Firefox companion 0.6.3.

The installed profile uses a per-download and shared per-origin ceiling of 16 with adaptive mode enabled; repository defaults stay at 8 for other installations. A request ceiling is not a universal speed optimum: complete-file timings must include disk writes, attachment processing, hashing and publication, and simultaneous jobs must be judged by aggregate completion time. Development-only WAN diagnostics stay in ignored artifacts. The 32 MiB queue balances slow requests and limits retry work; its 32 display groups are independent of the request ceiling. See [aria2's piece-selection documentation](https://aria2.github.io/manual/en/html/aria2c.html#cmdoption-stream-piece-selector) and [AWS's guidance to measure request concurrency and reuse connections](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-design-patterns.html).

Known-size downloads normally write to one destination-local staging file. Workers own disjoint offsets and flush buffers before checkpointing. The shared file is synced before durable ledger claims, batching routine checkpoints every five seconds and forcing them on pause/error/completion. A hard process exit can require downloading recent uncheckpointed bytes again. Legacy part files and unknown-size streams keep the buffered merge path. Files pass Windows Attachment Services, keep internet-zone metadata, get hashed, and are published without replacing an existing destination. A finalization journal recovers either side of publication. State files have synced backups; damaged JSON is quarantined and recovered, or startup stops without wiping history.

The local.5 update retries request-stage transport disconnects as well as interrupted bodies, using the existing bounded attempts/backoff and a fresh worker transport pool. Invalid request construction, authentication failures, unsafe redirects and representation validation remain failures. Adaptive mode resets a proven minimum count only after three consecutive averaged windows change in the same direction by more than 20%, measured at that proven count; brief dips/bursts cannot erase it. Lower-count trials remove a quarter of the workers, rounded down with a minimum of one, reducing the throughput sacrificed during exploration. Server throttling still halves requests immediately.

Checkpoint writers serialize separately from the live range ledger. Workers can finish a range or start their next request while a routine disk sync is pending; routine saves coalesce, while pause/error/final completion wait for a fresh serialized snapshot. Each snapshot still records only flushed, hashed prefixes, syncs the staging data first, then durably publishes the ledger. The native suite forces a pause with sixteen writers, checks every committed prefix digest and resumes to identical full output.

Windows publication runs on Tokio's blocking pool. A per-download publication lock serializes pause/cancel with the final rename while the record stays readable, so progress and other transfers can continue during slow file operations. Publication does not hold the global history-write lock; atomic no-replace moves and collision retries arbitrate names, while history snapshots/writes remain serialized. The durable journal and completed-state update keep their ordering. Once publication starts, pause/cancel immediately report that the file is being finalized, avoiding control timeouts or cancellation of an already committed publication. [Microsoft documents why synchronous I/O blocks its caller](https://learn.microsoft.com/en-us/windows/win32/fileio/synchronous-and-asynchronous-i-o); [Attachment Services can scan, alter or delete a file](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-iattachmentexecute-save), so integrity is still checked after that policy runs.

The companion journals browser ownership and uses persisted idempotent handoffs. It verifies a paused engine job, cancels the browser transfer, then commits the handoff. Lost replies and startup interruption can reconcile that journal. Capture can ask, auto-start, or stay in the browser; minimum size and site/type exclusions are available. Optional per-site authenticated GET support forwards only selected headers using a uniquely observed request and Firefox cookie store. Credentials stay in memory and cannot follow cross-origin redirects. After app restart, authenticated jobs need a fresh browser session/link. POST bodies, blobs and ambiguous sessions stay browser-managed.

Firefox's local fork ID is `{bb4d3986-35bd-4e55-bbcb-bb7f67894086}`; the host also accepts the upstream ID for compatibility. Firefox 140 or newer is required. Capture waits for initial bytes before pausing: Firefox's pause cancels its connection, and a zero-byte transfer cannot be resumed. A resumable Firefox pause reports `interrupted`, so acceptance, rollback and journal recovery check its paused/resumable flags. For permanent installation, sign the ZIP privately through Mozilla's **On your own** distribution workflow, supplying the companion build source when requested. Install its signed XPI in `about:addons`, then disable the old companion to avoid two interceptors. A signed add-on does not automatically update itself from an unpacked folder; later changes need a new version and signature.

Build and checks:

```powershell
npm ci
npm run build
npm run browser:check
npm run release:check
cargo test --manifest-path src-tauri/Cargo.toml --features tauri/custom-protocol --lib --locked
cargo clippy --manifest-path src-tauri/Cargo.toml --features tauri/custom-protocol --all-targets --locked -- -D warnings
cargo build --manifest-path src-tauri/Cargo.toml --release --features tauri/custom-protocol --bin fetchrail --locked
npm run browser:package:firefox
```

With the installed app idle and closed, `npm run engine:test` creates its own temporary profile and output folder. `FETCHRAIL_DATA_DIR` can select an absolute isolated profile; this skips native-host/startup registration. Set `FETCHRAIL_BENCHMARK=1` for alternating, digest-checked range/storage benchmarks; `FETCHRAIL_BENCHMARK_MIB` defaults to 32 and accepts 32..512 MiB in multiples of eight. `FETCHRAIL_IDM_BENCHMARK=1` optionally tests this PC's installed IDM when it is closed, using temporary test outputs and its documented `/d /p /f /n /q` arguments. IDM gets test history entries; its configuration is not changed. On this PC, launch native tests/installers from ordinary Windows context: Codex's MSIX AppData view can otherwise isolate registrations and settings.

The integration suite checks both companion APIs through the real host/engine, concurrent transfers/origin and bandwidth limits, byte identity, pause/restart, changed worker counts, ignored/invalid ranges, zero/unknown lengths, disconnects, Retry-After, authentication, credential isolation, trusted-link refresh, damaged parts, failed acceptance persistence, filename collisions, publication crash boundaries and Windows provenance. Two adaptive files also share a constrained host budget without mistaking queued workers for slower connections. Unit tests ensure FIFO waiters precede refills and cancellation cannot leave unused bandwidth reservations delaying later jobs. The Firefox package must also pass Mozilla's archive validator, not only source-directory lint.

This is an HTTP download improvement, not complete IDM feature parity. HLS/DASH segment selection and muxing, DRM, FTP/torrents, browser-generated exports, universal site adapters, real hardware power loss, network-share/disk-full acceptance and broad WAN benchmarks need separate implementation or verification. Loopback timings are controlled fixtures, not proof that Fetchrail is universally faster than IDM.
