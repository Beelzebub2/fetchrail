# Fetchrail: privacy-first reliability analytics and diagnostics — Codex handoff

Research checked **16 October 2026** against primary EU/Portuguese legal and regulator sources, Cloudflare's current documentation, and the Fetchrail source tree. The application is distributed in Europe, maintained from Portugal, and currently uses Cloudflare Workers Free. GDPR territorial applicability depends on the controller's establishment and processing/targeting facts under Article 3, **not on the geographical source of project funding alone**. **This is an engineering/legal research brief, not a legal opinion or a claim of certification.** An accountable controller must confirm the final legal analysis and notices before expanding collection.

## Instructions to Codex — use this as the implementation specification

You are implementing a production-grade, privacy-first **Fetchrail reliability observability system**, extending the existing v0.7.4 analytics rather than substituting a third-party tracker. The goal is to identify and fix stalled downloads, retries, server incompatibilities, bandwidth ceilings, broken resume, torrent failures, slow disk/verification/publication, crashes and user-facing regressions, including whether a 21,618,816,672-byte download can reach *durably completed* in approximately 180 seconds (which requires about **120.10 decimal MB/s end-to-end**).

1. First re-read this document, scoped `AGENTS.md`, the source links in section 2 and the live branch. Fetch origin, inspect the dirty tree and incoming commits, use a task branch, preserve other work and user data. If anything here differs from later legislation, installed code or a user's instruction, update the research and explain the difference.
2. Implement the work in small, reviewable, validated increments. Begin with an architecture/records-of-processing/privacy review and a typed measurement catalogue; build native instrumentation and privacy UI; extend the existing Worker only if necessary; ship a private operator report and optional incident export. Do not replace existing history, retention controls, browser integration, production keys or signing identities.
3. Treat **no collection before informed, purpose-specific, recorded opt-in** as the product default for *remote optional analytics*. Preserving the existing v1 grant authorizes **v1 fields only**. New telemetry fields or purposes require a new explicit v2 choice. Detailed support incidents require an independent *per-incident* review and permission. No consent, refusal, revoked consent, pre-consent downloads and stale scopes must generate **zero new outbound telemetry**. All ordinary downloads continue to work.
4. Reuse the current lightweight trace phases, outcome machinery, protected download history and performance diagnostics. Do not add a full OpenTelemetry collector, a new analytics SaaS, persistent advertising identifier, data lake, or generic log upload just because one exists. Build the simplest evidence pipeline that answers the actual questions.
5. **Do not deploy to Cloudflare, alter installed Fetchrail, publish browser packages, change secrets or post support data during design and source testing**. Prepare exact artifacts, tests, deployment plan and an operator checklist for review. Production rollout requires a verified migration, budget and privacy text.
6. Deliver a working implementation with tests and an evidence-backed readout. Do not stop after only a schema, mock dashboard, legal memo or synthetic-only tests. If actual production quota, regulatory approval or physical performance validation is unavailable, state that precise blocker rather than marking it done.

**Required acceptance outcome:** a user can explain what Fetchrail *observed* during a slow or failed download from a **private local report**, including events **leading up to** the incident; with new voluntary consent, the maintainer can see release/protocol/size-level failure causes and latency distributions **without learning what anyone downloaded, which sites they visited or who they are**. An incident can be shared only after a separate user preview. Distinguish a proven cause, a supported hypothesis, and insufficient evidence. Integrity, resume safety, the signed browser companion and app behavior must remain intact. **Do not promise that telemetry alone can determine every external root cause or replace reproduction, code review and profiling.**

## 2. Legal and compliance research: classify obligations correctly

### Sources of authority and their scope

1. **EU GDPR, Regulation (EU) 2016/679** — [official consolidated text](https://eur-lex.europa.eu/eli/reg/2016/679). Article 3 (territorial scope), 5 (lawfulness, minimization, purpose limitation, accuracy, storage limitation, integrity, accountability), 6 (lawful basis), 7 (consent/withdrawal), 8 (children), 12–15 and 17–21 (transparency/rights), 13 (notice), 24–25 (controller responsibility/design and default), 28 (processors), 30 (records), 32–34 (security and breaches), 35–36 (DPIA and prior consultation), 44–49 (international transfers). **GDPR does not automatically require all data to be physically stored in the EU.** International transfers instead require applicable legal mechanisms and assessment.
2. **Portugal, Law 41/2004, Article 5, as amended** — [Diário da República, consolidated law](https://diariodarepublica.pt/dr/legislacao-consolidada/lei/2004-106523049). Prior informed consent is the default for nonexempt storage of/access to information on terminal equipment. The narrow exceptions concern communication transmission and service functions *strictly necessary* for the service expressly requested. Rely on the **consolidated 2012-amended wording**, not the obsolete 2004 wording about a mere right to refuse.
3. **EU ePrivacy Directive 2002/58/EC, Article 5(3), as amended by 2009/136/EC** — [consolidated EU text](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A02002L0058-20091219). Applies to storing/accessing device information, including methods other than ordinary browser cookies.
4. **EDPB Guidelines 2/2023, final version, 16 October 2024** — [technical scope of Article 5(3)](https://www.edpb.europa.eu/our-work-tools/our-documents/guidelines/guidelines-22023-technical-scope-art-53-eprivacy-directive_en). Local computation followed by externally instructed retrieval can count as accessing terminal information; renaming telemetry to 'anonymous diagnostics' does not remove the terminal-access question.
5. **EDPB Guidelines 05/2020** — [consent](https://www.edpb.europa.eu/documents/guideline/guidelines-052020-on-consent-under-regulation-2016679_en); [EDPB practical controller guidance](https://www.edpb.europa.eu/sme/be-compliant/process-personal-data-lawfully_en). Consent must be affirmative, specific, informed, demonstrable, freely given and withdrawable as easily as granted. Separate purposes; no preselected boxes or penalty for refusal.
6. **EDPB Guidelines 4/2019** — [Article 25: data protection by design/default](https://www.edpb.europa.eu/documents/guideline/guidelines-42019-on-article-25-data-protection-by-design-and-by-default_en). Build prevention into API types and default configuration, not solely policy prose.
7. **Portugal, Law 58/2019** — [Diário da República](https://diariodarepublica.pt/dr/detalhe/lei/58-2019-123815982). Article 16 sets **13 years** for the GDPR Article 8 consent route in directly offered information-society services; lower ages need qualifying parental consent. This matters if Fetchrail intentionally targets children, not as an excuse to collect date of birth from all users.
8. **Portugal, CNPD** — [DPIA guidance](https://www.cnpd.pt/organizacoes/outras-obrigacoes/avaliacao-de-impacto/), including the mandatory list under CNPD Regulation 798/2018; [CNPD collection of EDPB guidelines](https://www.cnpd.pt/organizacoes/orientacoes-e-recomendacoes/diretrizes-do-comite-europeu/). Conduct/document an Article 35 risk screening; a DPIA is required where the processing is likely high-risk or on the applicable CNPD list. **Do not claim a DPIA is mandatory for every small aggregate telemetry system**, nor that consent automatically eliminates DPIA duties. If high residual risk remains, assess Article 36 consultation.
9. **GDPR breach handling** — [EDPB guidance](https://www.edpb.europa.eu/sme/assess-the-risks/data-breaches_en): document breaches, notify the supervisory authority within 72 hours when Article 33 applies, and affected people when Article 34 requires it. Cloudflare must alert the controller without undue delay under the DPA.
10. **Cloudflare controller/processor obligations** — [Cloudflare DPA v6.4, effective 3 April 2026](https://www.cloudflare.com/en-gb/cloudflare-customer-dpa/) and [SCCs](https://www.cloudflare.com/en-gb/cloudflare-customer-scc/). Record whether RRMTools is controller, Cloudflare a processor for the relevant service, the accepted DPA, subprocessors, retention, transfer mechanism and transfer impact assessment where relevant. Cloudflare also sees IP and may process transport/security metadata; absence of IP columns in our SQLite tables is **not** proof that no personal-data processing occurs.
11. **Storage region limitations** — [Cloudflare Durable Objects data-location docs](https://developers.cloudflare.com/durable-objects/reference/data-location/), [Data Localization Suite](https://developers.cloudflare.com/data-localization/), [Durable Objects / Regional Services](https://developers.cloudflare.com/data-localization/how-to/durable-objects/). `namespace.jurisdiction("eu")` restricts where that Durable Object runs/stores data, while Workers may reach it from elsewhere and some ID/billing metadata can be logged outside the jurisdiction. End-to-end EU-only TLS processing and customer metadata boundaries require separately entitled Data Localization Suite features; **the complete suite is an Enterprise paid add-on**. A named EU DO is a *different object ID* from the current global named DO: do not assume a transparent in-place migration.
12. **Transport and measurement best practice (technical, not law)** — [HTTP Semantics RFC 9110 (range/validator/status rules)](https://www.rfc-editor.org/rfc/rfc9110.html), [OpenTelemetry HTTP metric semantics](https://opentelemetry.io/docs/specs/semconv/http/http-metrics/) and [Cloudflare DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/). Use stable units, explicit histogram boundaries and vetted finite dimensions; **do not export OpenTelemetry's generic `server.address`**, because a download-server address is private source data here.

Additional advice: French CNIL audience-measurement exceptions cannot be presumed to apply in Portugal. Draft EDPB legitimate-interest/pseudonymization documents are not necessarily final law; do not use draft guidance as a substitute for consent or for a legal-basis analysis. Confirm current legal status at release, not just at authoring time.

## 3. Product objective, metrics and honest denominators

### Primary engineering KPIs

1. **Verified durable completion rate**: accepted *eligible logical transfers* reaching integrity-verified, flushed/published output **and successfully persisted Completed catalog** / all eligible logical transfers with a genuinely observed terminal outcome in the reporting window. Cancelled by user reported separately; unfinished transfer state and suppressed reports must not be silently counted as successful or failed. For torrents, define separately whether 'complete' means selected payload verified, fully downloaded, or still seeding. Report count and observation coverage along with rate.
2. **End-to-end completed time distribution (p50/p95)**: monotonic accept-to-durable-catalog-confirmation duration, by coarse size tier and protocol, excluding deliberately user-scheduled/paused time only in *separately named* 'active-operation' metrics. Report wall-time and active-time metrics separately, never substitute transfer-body speed for end-to-end success.
3. **Recoverable failure and stall burden**: proportion of terminal failures by vetted cause + retries, time stalled without progress while an active receive should be advancing, and wasted or retransferred bytes in broad buckets. A recovered retry is a recovery event, not a second logical transfer.

**Supporting drivers:** admission/origin wait; initial metadata/head/range validation; response-header delay; first body-byte; receive throughput (full 5s / 10s windows); HTTP 429/503/Retry-After backoff; TLS/connect/timeout; streaming/writer stalls; checkpoint flush; hash verification; attachment/security scan; publish rename/sync; catalog durability; recovery. Store per-stage histograms and event counts, **not** continuous remote timelines. Keep protocol HTTP vs torrent and broad size tier separated to prevent Simpson's paradox. Where useful, distinguish explicit user throttle and server refusal from engine-caused slowness.

**Privacy and reliability guardrails:** percentage of requests emitted with consent disabled = **0**; unknown/non-allowlisted fields accepted = **0**; raw identifiers in transmitted payload = **0**; integrity regressions = **0**; release-service starvation = **0**; overhead in an A/B controlled workload target ≤1% median throughput loss and ≤2% p95 end-to-end latency change (provisional engineering gates; repeat tests if noise exceeds this). No extra synchronous disk write in the hot receive path.

### Nonnegotiable measurement semantics

* Keep logical-download, transfer attempt, HTTP range request and browser handoff as **four different grains**. Store stable internal IDs only in existing **local** state, never in remote metrics. A retry does not increase `downloads_added` or count another failed logical download. A recovered transfer does not backfill events from a period before consent.
* Time durations with a monotonic clock. Use UTC **only** for the server's daily aggregate partition; send no exact download start/finish timestamps, device clock, time zone or high-resolution sequence that forms a behavioral pattern.
* `received_wire_bytes`, `new_verified_bytes`, `durable_written_bytes`, `retransferred_bytes`, `total_bytes` and `output_verified_bytes` are distinct. Don't sum parallel range throughputs to invent completion throughput or count previously downloaded bytes twice.
* Explicitly define boundaries for queue wait, user pause, scheduling, global/per-file cap, response read, connection/retry waiting, disk flush, antivirus/Attachment Services, SHA-256 and atomic publication. Some spans overlap; do **not** imply phase sums equal total wall time unless they are measured as mutually exclusive critical-path states.
* Stall: active eligible transfer with **zero increase in actual received bytes for a specified interval** (e.g., 2 seconds), after excluding user pause, schedule, intentional cap, acknowledged server backoff and finalization. Record how many stalls and their duration buckets; do not classify every long synchronous flush as a network stall.
* Rate `received_bytes / actively measured body time` is a separate network statistic. Rate `verified output bytes / accept-to-durable-completion seconds` is *end-to-end*. Explicitly handle unknown length, partial/resumed transfers, file changes and data still in unflushed buffers. 'Completed' for analytics requires the real existing safety boundary, not an optimistic UI event.
* Percentiles must be derived from a mergeable bounded histogram or actual local samples, never arithmetic averages of per-client p95 values; report count, missingness, clipping/saturation and confidence. Suppress p95 conclusions for very small counts (initial operational gate at least 20 observations) and avoid p99 until samples are numerous and stable. Do not present unique users, sessions or real population failure rates from the opt-in sample.
* Histograms use a **small shared predefined set of boundaries** with fixed units (e.g. durations in milliseconds; receive rate MB/s in decimal units; sizes in MiB/GiB). Use counted buckets and saturating arithmetic; remain memory/CPU bounded. Include explicit version in schema so changes to bucket boundaries never silently merge incompatible data.

## 4. Recommended architecture: local evidence + voluntary fleet aggregates

### Lane A: always-functional local engine and user-controlled troubleshooting

* Preserve existing functional download progress, encrypted Windows download catalog and local tuning as service features. Keep transfer timing cheap; when analytics is off, remote emission, persistent telemetry queue, endpoint lookup and extra *remote-purpose* data gathering are off. Determine and document whether minimal local troubleshooting observations are part of the user's requested service or require a separate local control under the legal assessment.
* Add typed `TransferHealth` sampling at lifecycle boundaries using cheap `Instant`, atomics and bounded histograms. The ordinary UI can display precise **local** stage timing, a stall reason, retries, received/durable bytes, current caps and error classes for the user's own download. Local details do not become remotely accessible just because the user views a panel.
* Provide **Troubleshoot this download** with a bounded, private, **on-device only pre-incident flight recorder** of safe, minimal numeric operational transitions already needed by the local engine; retain a small volatile ring **while the transfer runs**, including before the user opens Troubleshoot. On stall/failure, preserve the currently available local diagnostic snapshot until the transfer is closed or the app exits, so the user can inspect what happened **before** noticing a problem. The ring must not itself add network requests, new source inspection, persistent tracking identifiers or automatic upload, and it must be accounted for in the terminal-access/legal review. Expose the last N stage transitions, stalls, retry causes, HTTP classification, verified checkpoint, finalization and unknown/missing periods. A user-requested high-resolution trace can add bounded detail for a future reproduction only; never enable the current unrestricted developer test trace in production.
* **Crash and power-loss honesty:** an in-memory ring is lost on hard termination. Offer a **separate, clearly disclosed user-enabled local crash-breadcrumb option** if post-restart evidence is needed; use only sanitized minimal stage/counter checkpoints, existing private atomic storage patterns, finite size/frequency, encryption/protection where applicable, a clear expiry and **Delete local diagnostic history**. Never synchronously write a breadcrumb on each received chunk or weaken existing flush/recovery guarantees. Do not claim post-crash reconstruction if the option was off or the final breadcrumb wasn't durable. Default remains no new persistent diagnostic history until this option is explicitly chosen and legally reviewed.
* A more persistent local report needs an explicit setting, tight limits (e.g., last 20 selected transfers or 7 days), protected permissions/encryption where feasible, and a Clear control. Do not log raw HTTP errors/stack traces by default: they can include credentials or paths. A local-only report contains per-stage cause evidence that is **not reconstructible** from anonymous cloud daily aggregates.
* Reuse `engine/trace.rs` phase names and tests as the design baseline. Its current test-only `FETCHRAIL_TEST_TRACE` has a deliberate isolation gate. Do **not** enable developer trace by broadening this environment variable in ordinary installations; introduce a separate, audited safe typed collector.
* Enable a **Copy safe report / Export safe report** action with a user-visible field-by-field preview, an optional one-time 'include additional technical data' selection (still redacted and reviewed), explicit warnings about uploading to *public* GitHub issues and easy cancellation. Offline exports are a useful first phase and require no new server incident database.

### Lane B: new optional aggregated developer analytics

* Consent `product-quality-v2` is separate from old `product-improvement-v1` until a reviewed migration explicitly redefines it. Settings allow voluntary choice; an old v1 grant sends only v1 counters. No backfill or synthetic catch-up. A v2 denial does not disable v1 if the user keeps v1 enabled, and vice versa.
* Keep a single native background batching loop with delayed missed ticks and 30-minute maximum periodic cadence, a finite allowlisted payload, zero cookie jar, zero download credentials, no redirects and a short timeout. Prefer preserving the existing best-effort *discard-on-exit/failure* semantics; any on-disk retry queue is a privacy-scope expansion requiring separate review, retention and revocation tests.
* Generate only preaggregated counters + bounded bucket arrays on the client. Use **no unique installation ID, stable pseudonym, nonce persisted between reports, hashed host/domain, IP, exact timestamp, machine fingerprint or stable crash identifier**. If a genuinely needed future deduplication mechanism conflicts with this, stop and present the privacy and accuracy trade-off before implementing it.
* Suggested typed envelope (illustrative **not** an approved final schema):

```json
{
  "schema": 2,
  "purpose": "product-quality-v2",
  "version": "0.7.5",
  "os": "windows",
  "arch": "x64",
  "counters": {
    "http_accepted": 5,
    "http_verified_durable": 3,
    "http_503": 2
  },
  "histograms": {
    "http_active_body_ms_v1": [0, 0, 1, 1, 1, 0, 0, 0],
    "http_durable_finalize_ms_v1": [1, 1, 1, 0, 0, 0, 0, 0]
  }
}
```

* Prefer a proven payload under 4 KiB (the current v1 is 2 KiB); run fixed-size validation and ensure the server and client enforce the same schema. No arbitrary names/tags, unbounded arrays, negative numbers or client-picked dimensions. Group at most by UTC date, stable semantic release, broad OS and possibly arch; avoid large cross-products of failure/size/network combinations. Do not expose small cells to public users, and don't claim a minimum **number of people** when you can only count reports.
* Server uses its **receipt day** (UTC); does not trust client timestamps. Typed validation rejects old-and-new purpose blending, encoded/query/cookie requests, unknown fields, oversize, absurd counts and query dimensions. Immediately aggregate into SQLite; never write raw submitted envelopes, exact receive timestamps or request IPs to our application database. Keep Cloudflare invocation logs/traces disabled for telemetry; verify metadata and logs at the vendor boundary. Aggregate reads require private authorization with rotation and operator-only access.
* The public intake currently **cannot prove a caller really opted in**. Fake-but-schema-valid reports can skew totals. Avoid claiming exact prevalence or fraud resistance; don't introduce device IDs or fingerprinting to solve it. Document quality limits and use bounded intake, Cloudflare-provided coarse rate limiting as separately documented/security-reviewed if needed, and synthetic source-backed validation.

### Lane C: one-time incident sharing (independent and optional)

Stage 1: local safe export + user-mediated sharing through a private channel. Stage 2 **only if needed**: a dedicated incident endpoint/storage with separate, explicit per-incident approval, bounded size, type-checked fields, encrypted storage, an access-controlled support UI, deletion/expiry and a strict upload abuse policy. Keep reports isolated from fleet analytics. A short-lived **per-submission** reference (no persistent device identity) can help the person retrieve/delete their submitted report; treat the reference as personal/pseudonymous where applicable. If authenticating the uploader requires tracking, use an explicit trade-off and redesign, not hidden identifiers.

Never upload raw request headers, cookies, proxy credentials, bearer tokens, magnets, tracker URLs, peer IPs, filenames, full URLs or query strings, path/home/user names, arbitrary diagnostic errors, stack traces, personal network information or the downloaded bytes. Allowlisted incident report can contain **per-stage durations, safe numeric errors, retry categories and sanitized bounded protocol metadata**. Perform field selection at the source plus a second server-side structural check. String-replacement redaction alone is not sufficient.

## 5. Cloudflare choice, quotas, geographical integrity and retention

**Default choice: retain Workers + SQLite Durable Objects** and the existing Worker route. D1 and R2 are unnecessary for small aggregate counters. Do not turn on generic Workers tracing, Logpush or RUM for arbitrary client metadata. Avoid a new collector and permanent event store. Protected self-hosted reports/querying are sufficient.

Cloudflare's pricing documentation checked 16 October 2026 describes Workers Free SQLite DO allowances as **100,000 DO requests/day**, **5,000,000 rows read/day**, **100,000 rows written/day**, and **5 GB total SQLite storage**. The limits page states a general **10 GB per-DO maximum on Paid**; the Free plan's 5 GB account-wide quota remains the operative stricter storage ceiling. **Source conflict:** Cloudflare's product marketing page currently advertises *50 million* Free SQL row reads/day while its detailed pricing table says *5 million/day*. Budget against the smaller documented figure unless account-level metering/support establishes a different enforceable limit. Worker quotas are separate. DO alarms, index writes, deletions and other app uses also consume quota. See [pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [limits](https://developers.cloudflare.com/durable-objects/platform/limits/) and the [product marketing page](https://www.cloudflare.com/products/durable-objects/). The current code's **20,000 reports/hour** ceiling could permit 480,000/day and blow past Free's daily rows-written allowance; fix this with a **shared UTC-day budget** below the binding quota, leaving headroom for updater and all other services. Start with a conservative cap such as 20,000 accepted report batches/day total, subject to measured row/write usage and account-wide usage verification. The service must drop analytics gracefully on exhaustion and **never starve update or download operation**.

**Data locality decision:** The current `daily-v1` object isn't bound to a jurisdiction. Decide explicitly whether the next aggregate store should be EU-jurisdiction, check Cloudflare plan support, processor contract and effects on release operations. An EU jurisdiction-specific `getByName` is a different durable object: prepare a safe read-only old-data export and staged, validated copy only if authorized and if reidentification/cross-border impact permits it; otherwise allow v1 to age out under existing 30-day retention while v2 starts in the restricted region. Confirm the actual selected residency and provider metadata before updating the public notice. **EU-object residency alone does not guarantee EU-only TLS termination/logging** and is not by itself proof of GDPR compliance. Data Localization Suite's stronger request/metadata controls may require paid entitlements.

| Dataset | Intended lifetime | Storage/rights |
| --- | --- | --- |
| Local download state/history | User-controlled, currently persists until removed | Existing privacy-protected local state, never imported into telemetry. |
| Extra local troubleshooting buffer | Session only by default; optional explicitly saved 7 days / last 20 selected cases as candidate policy | User can clear/delete; protect file permissions and contents. |
| Fleet analytics | Latest 30 UTC calendar days | Only preaggregated daily counts/histograms; nightly/hourly prune even without new reports. Cloudflare SQLite PITR may retain recoverable snapshots for **up to 30 additional days**, which the notice must disclose. |
| Individually submitted incident | No remote storage in phase 1; if stage 2, choose e.g. 7 days after closure with **hard 30-day cap**, subject to documented service need | Preview + granular permission; controlled support access; early erasure where applicable; separate storage and deletion audit. |
| Consent evidence | Device-local purpose/schema/decision timestamp/version as needed for accountability; no remote user identifier | Consent/refusal survives restart and migration. Withdrawal cannot be silently reversed by stale settings, failed writes or restore paths. |

Storage/processing security: TLS, strict JSON content type and size/time bounds, no secret in client, least-privilege analytics-read tokens, scoped operator roles, signed change review, parameterized SQL, daily UTC cap, cardinality cap, alarm lifecycle, write/read amplification measurement, safeguards against SQL/JSON bombs, data deletion verification and no public dashboard. Run incident access audits **without storing download contents or user identifiers**; if the support service retains personal data, keep separate protected audit records with a documented finite retention.

## 6. Product UX and trust

1. Keep initial balanced **Allow** / **No thanks** consent prompt in the native app, with summary, accessible details, purpose, recipient, exact categories, approximate frequency, retention, withdrawal and separate support sharing. Reject, close and Escape must stay equivalent refusal. Navigation/downloads never blocked if the user declines.
2. Settings → Privacy should show independently switchable **product improvement v1** and **download reliability v2** purposes or a carefully migrated combined consent only if legally and technically justified. Version every consent scope and retain the former choice; do not auto-enable v2 on v1 installations. Screen-readers, keyboard focus, high contrast, reduced motion, zoom and narrow windows must work.
3. A **Download health / Troubleshoot** panel must show the *user's own* explicit, meaningful stage timeline and categorized diagnoses: 'server rate-limited the request', 'received bytes stopped progressing', 'disk flush took 18s', 'waiting for virus scan', 'hash verified, catalog write pending'. These are examples; never assert one unless stage evidence proves it.
4. A privacy-safe **Preview what would be sent** should print the actual serializer output, with exact units/buckets and no invisible extra fields. A separate **Share this incident** must display user-visible categories/retention and send nothing until confirmed.
5. Local report and privacy UI must plainly distinguish **network speed during receiving** from **end-to-end time until safe Completed**. Show size, queued/pause/backoff time, received/committed bytes, stage maxima, retries, finalization time, and clarity about unknown data. 100 MB/s sustained during download does not imply 100 MB/s of durable completed work.
6. Update `website/public/privacy.html`, `docs/analytics.md`, browser policy text if browser code changes, local settings disclosures and screenshots/examples together. No 'GDPR certified', 'fully anonymous', '100% EU-hosted' or 'no user data leaves your PC' claims unless precisely and independently substantiated.

## 7. Instrumentation plan at the actual code seams

* Start from `engine.rs` creation and admission: `analytics.prepare` and `register_analytics` only after successful durable addition; distinguish provisional extension handoff and eventual commit. Document cross-process download/torrent semantics.
* Extend the safe observer around `emit_record`, `observe_analytics` and torrent state transitions. Count terminal outcomes **after safe lifecycle and catalog commit**, not before data durability is established; ensure no duplicate terminal emits, lost final outcome or retry double count.
* Reuse phase vocabulary in `engine/trace.rs` (`Probe`, `Origin`, `Global`, `Headers`, `Body`, `Limiter`, `Write`, `Flush`, `Sync`, `Checkpoint`, `Retry`, `Assembly`, `Attachment`, `Verify`, `Journal`, `Publish`, `Catalog`) and safe coarse `RetryCause` buckets. Add any phase only for a distinct issue it helps resolve; the existing development trace remains isolated.
* Distinguish `HTTP 206` valid ranges, `200` ignoring Range, inconsistent `Content-Range`, strong validator changed, backoff to `429/503`, transient connection recovery and cancellation races. Never transmit response payload, validators or domain. Check RFC 9110 and existing resume/integrity tests before modifying any error path.
* Instrument **real** disk and commit boundaries: writer queue, flush/fsync, SHA-256, attachment service, publish without replacement, journal, catalog persist. Avoid reporting 'durable success' before flush and final committed catalog and account for recovery after crash.
* Browser native messaging should be measured at explicit state transitions with category-only error codes; do not add a browser-side analytics SDK. Torrent state transitions may include metadata, piece verification, selected files and seeding separately, but no trackers/peers/infohash.
* UI should receive local progress/health updates at bounded existing event cadence; avoid extra 180ms-per-download events or performance degradation at 10,000 history records.
* Bound locks, memory and histogram cardinality. Use typed Rust enums to eliminate accidental PII conversion; workers accept schema allowlist only. Do not serialize any `DownloadRecord`, settings object or arbitrary `serde_json::Value` into remote metrics.

## 8. Statistical quality, prioritization and honest reporting

**Fleet dashboards are advisory:** recipients voluntarily opt in; app launches are not people; some clients leave within 30 minutes; errors/reports can be dropped, forged or duplicated when there is no unique authenticated identity. For any chart, show schema/release, dates, eligible counts, observations, suppressed groups, missingness and measurement definition. Never compute a 'failure probability among all users' from those reports.

**Daily operator report:** by stable release and broad protocol, show durable completion outcomes, failure and retry categories, histogram-derived p50/p95 finalization and end-to-end timing with sample counts, stall rates and guardrail breaches. Compare before/after version using *the same consent scope, definition and size-band*; avoid interpreting a tiny skewed sample as statistical proof.

**Investigation decision tree:**

1. Low end-to-end speed with healthy receive rate → compare hash, attachment, flush, publication and catalog timing.
2. Low receive rate with no user speed cap → inspect parallelism, headers/first-byte delay, HTTP version, queue/origin admission, server 429/503, Retry-After, resets and slow-peer recovery.
3. Failed or broken resume → separate source ETag/range change, incomplete body, restart recovery, stale checkpoint, checksum and atomic publish conflict.
4. Torrent poor reliability → metadata admission, peers availability *count bucket only*, piece verification and local disk, without source identity.
5. Browser downloads missing → offered/accepted/committed native handoff stage and extension platform bucket (only after appropriate consent).

Keep short, documented examples of an evidence-supported actionable diagnosis; never auto-blame the ISP or server based solely on low throughput. Where sample size is too small, say **insufficient evidence** and offer the local troubleshooting path.

### Diagnostic completeness and proof-of-cause contract

**No analytics system can reconstruct an event it never measured or inspect the internals of a third-party server, ISP, OS driver or antivirus service.** The practical goal is to account for every phase Fetchrail controls, surface what it observed at subsystem boundaries, and state what evidence is still missing. Implement the following as a verifiable product contract, rather than promising 'every issue can be fixed just by looking at analytics'.

| Evidence level | What a maintainer can establish | What it cannot establish alone |
| --- | --- | --- |
| Consent-based **fleet aggregates** | Which release, broad protocol, size tier, stage or vetted failure class regressed; sample counts and latency distributions; broad direction of fixes | Exact sequence/cause of one user's download, unique users, individual host behavior, debugging variables or events from opted-out clients |
| User's **local flight recorder** | Per-transfer order of waits, retries, client caps, bytes received versus durable, ranges, checks, hash/publish/catalog timing, recent stall or error class | Internal reasons for delays in the source server, ISP routers, Windows kernel, storage firmware or antivirus; events missed before observation or after a hard crash |
| **Separately reviewed incident export** | Sanitized reproduction context and causal ordering across the stages for one selected incident, without remote installation identity or sensitive source data | A claim of root cause where local timestamps only reveal symptoms; complete histories not retained on the user's device |
| **Controlled reproduction + targeted profiling** | Whether the suspected code path causes the failure; whether the fix improves correct, secure, durable completion under comparable conditions | Certainty that every real-world endpoint or network will behave like the fixture |

**Correlate stages *locally*.** The private observer may associate each stage, attempt and range with its existing local transfer identifier so that the user sees a coherent story; that identifier must never leave the device in routine fleet telemetry. Preserve a clean event sequence across asynchronous workers, retries and restart/recovery. Represent concurrent spans and critical-path blocking explicitly: adding overlapping phase durations is invalid. Capture, where available and allowed, connection establishment/timeout categories, HTTP protocol, range validation, intentional throttling, origin/global admission, capacity/slot occupancy, backoff, active receive windows, received and durable bytes, disk queue/write/flush, verification, attachment processing, publication and history commit. Report **unobserved** or **not instrumented** rather than inventing a zero-duration phase.

**Issue reports must be actionable and falsifiable.** For any local incident, show: (1) the observed symptom and actual end-to-end impact, (2) directly observed stage(s) accounting for the delay or failure, (3) supporting measurements and what was unobserved, (4) a confidence/evidence category **Observed / Likely / Unknown**, and (5) the next smallest safe diagnostic or reproduction that could distinguish remaining hypotheses. Never report 'ISP fault' just because a transfer is slow or 'server bug' just because an HTTP response was delayed. For each statistically elevated fleet issue, link the metric name and version to a concrete local test recipe and acceptance threshold, not a dashboard-only guess.

**Coverage tests must deliberately exercise known root causes.** Build deterministic fault fixtures for refused ranges, changed validators, server throttling, DNS/TLS/connect failures, timeout during body, missing progress, scheduler/user pause, limiter, disk backpressure, flush/sync delay, hash mismatch, Windows Attachment Services delay, no-clobber conflict, catalog write failure, cancellation at finalization, browser handoff failure, torrent verification/recovery, forced process exit and power-loss-style replay. For each, assert that the diagnostic report identifies the **correct observed stage** with the correct byte/time accounting, appropriate confidence, and no fabricated external cause; ensure stale/incomplete/broken measurement is visibly **Unknown**. Include at least one problem occurring **before** the user opens Troubleshoot, one without an opt-in remote analytics grant, one where the app terminates before snapshot persistence, and one that only reproduces under realistic hardware/network tests. Benchmark recorder overhead under existing throughput and memory limits.

**Release sign-off requires a coverage matrix** mapping each known failure scenario to its instrumentation point, local display, optional remote aggregate (or 'not collected'), reproduction recipe, expected confidence and passing fixture. Any uninstrumented critical transition, discovered blind spot, fatal exception without pre-incident evidence or unsupported causal claim must be called out as an open limitation and assigned to a follow-up. A passing dashboard build is not diagnostic completeness.

## 9. Threat model and security tests

**Adversaries/failures:** accidental PII emission from nested payloads and arbitrary `error.to_string()`; telemetry fired before consent or after revoke; consent reset/restore; exposure of signed download URLs in crash data; privacy regression in browser handoff; forged anonymous telemetry and quota attacks; operator read token leak; SQL abuse; identification through rare per-day/version/dimension groups; failed eviction/pruning/PITR; release service starved by analytics; logging/proxy metadata outside claimed EU; real download slowdown from metrics locks.

Required tests:

* **Consent matrix:** untouched install, declined (including close/Escape), v1-only upgrade, v2 granted, v2 rejected, detailed per-incident refused, v1/v2 withdrawn mid-batch/mid-send, scope/schema change, post-restart, corrupted/permission-denied settings, stale simultaneous settings update, pre-consent task completing later and old task finishing after revoke/regrant. Assert **no new unapproved network payload** and no silent reenable.
* **Poisoned source fixture:** inject sentinel credentials into signed URL, query, filenames, home path, HTTP Cookie/Authorization/Referer, proxy password, torrent tracker/infohash/peer, error stack and embedded JSON fields. Scan native serializer, request, Worker aggregate, private operator output, local *safe* export, logs and crash paths. Sentinels absent everywhere outside intentionally protected local operational state.
* **Metric validity:** randomized event transitions and model-based state tests for one accepted logical download and one terminal event; failure/retry/recovery, pause/cancel, hung/small/unknown-length/very-large torrents and HTTP, range change, already-existing output; stable histogram buckets and overflow; end-to-end duration must end at durable completion.
* **Worker intake:** oversized payload, slow body, forged enum/unknown field, negative/float/count-overflow, semver anomalies, copied cookies/headers, query strings, purpose mismatch, old-v1 compatibility, replay across scope, hourly and **daily** quotas, per-day 64-dimension cap or revised bound, alarm expiry and SQLite restart, absence of identifiable metadata in logs/database. Test read-token/role failures and SQL query bounds.
* **Privacy compliance integration:** policy and app disclosures reflect actual emitted schema and Cloudflare jurisdiction; stored retention, backups and PITR disclosed; DSAR/incident deletion process demonstrated; DPIA screen/ROPA/DPA decision documents present before rollout. Test actual public URL routing without sending live personal data.
* **Performance/correctness:** run deterministic local HTTP fixtures with slow chunks, HTTP/1.1 and HTTP/2, 206/200/416, Retry-After, 429/503, checksum errors, antivirus delays, disk stalls and crash/restart; use end-to-end same-byte/same-hash confirmed output. A/B telemetry off/on at 10/100/1000 history records plus at least one sustained 20+ GiB representative transfer on appropriate hardware, interleaved trials; compare process CPU/memory, bytes written, telemetry request count, p95 UI latency, real active receive and durable completion. Don't manipulate user downloads for tests; use isolated roots.
* **Release compatibility:** `npm run build`, `npm run analytics:ui` (Playwright installed as required), `npm run browser:check`, `npm run updates:test`, native `cargo test --manifest-path src-tauri/Cargo.toml --locked --lib`, targeted engine/torrent/desktop regression checks for touched code. Read repository pre-Cargo instructions if present; do not trust isolated synthetic mocks as proof of real-world throughput.
