## Actual Cloudflare qualification

A separately authenticated temporary Worker, `fetchrail-reliability-check-20261018`, used a **new synthetic-only SQLite namespace**, with no production analytics/feed bindings, no assets, no logs or traces. Source `update-service/analytics.mjs` SHA-256 was `CB5F27B1FD77AE3E31A186E3B7E75E99BAF674261696AAA9262D554E04490773`.

The temporary bundle wrapped each original SQL execution, fully consumed the cursor, and recorded its actual `rowsRead`/`rowsWritten`; SQL and transaction decisions were unchanged. Fifteen synthetic accepted batches covered usage v1, per-run diagnostic summary and v2. Initial dimension insertion measured 4 written rows; repeated batches measured **8 read / 3 written rows** each in this small database. This measures cursor billing units, not total account billing or peak-retention cost. At 20,000 batches, 3 steady writes implies 60,000 writes before new groups, expiry, alarms and other services. Conservative Free-tier/account-wide budgeting still applies.

Missing and incorrect credentials returned 401. The actual scheduler alarm removed synthetic expired rows from both schemas. Actual PITR restored two expired rows; the next report pruned them before exposure, and a subsequent inspection found zero expired rows. The deliberate object abort during restoration returned HTTP 500, as expected; restoration was proved by the restored rows, not that response. The test then cleared storage. Cloudflare confirmed deletion of the temporary Worker and its implemented namespace. Local detailed evidence is ignored at `artifacts/reliability/provider-qualification.json`; it contains no credential.

Initial production inspection found invocation logs and traces disabled, existing analytics/release-feed namespace identities intact, no v2 enable variable, and **no analytics-read secret configured**. ## Remaining acceptance

The pre-observer optimized baseline is `e0c9fc6`; its executable SHA-256 is `EC159A7ADD8D600C5C8237B3AEB2C4E14B424AA38E233D5D795C1B5CA2A6F409`. The Windows observer test executable SHA-256 is `8C41AD978165E8E5FF7F708C083128FAB541A28CB8E2CD5340FD1BD6DD6542CC`. Both are archived **0.7.4 test builds**, qualifying the observer implementation before the version/notice-only edits; they are not installers or final 0.7.5 artifacts.

Two full UI passes each performed 800 real search input-to-render/two-frame observations across baseline/candidate at 10/100/1,000/10,000 history rows. The repeated pass asserts all samples occurred during active capped reception and verifies every output hash/catalog. At 10,000 rows its candidate p95 was **19.6 ms**, baseline **20.3 ms**, from 100 observations each. These are render-frame observations, not hardware input/presentation measurements. Native-process CPU/RAM exclude WebView2 children. Detailed evidence: `artifacts/reliability/workload-92f3a566-a972-4973-a0b7-c45a60690798.json` (first UI pass has the earlier post-capture trace clock and is not used for durable timing).

The first matched ABBA pass verified four **21 GiB** generated loopback outputs and six smaller history-scaling cases. Its request-to-acknowledged-catalog clock uses same-host dispatch UTC and the actual catalog span end, checks clock drift, and excludes later developer-report writes. Baseline large durations were **169.648 / 205.069 s**, candidate **193.030 / 187.648 s**. Median receiving rates were **135.544 / 131.900 MB/s** respectively; median catalog timing was about **1.59% longer** for the candidate. With only two large trials per build and substantial baseline variation, the **≤1% throughput / ≤2% p95 latency target is unproved**, and a population p95 cannot be established. This is not proof that the recorder caused the difference. A counterbalanced BAAB repeat is required before accepting overhead. Evidence: `artifacts/reliability/workload-c657638c-47c6-49b2-9957-da985fe10f3a.json`.

The actual observer recorded writes awaiting up to 2.997 s, sync calls up to 6.618 s and scan/hash overlap around 17.8–19.4 s in those large fixtures. These are measured API/worker boundaries, not proof of disk-device utilization or antivirus internals. No WAN or universal performance conclusion is asserted.
