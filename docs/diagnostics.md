# Measured diagnostics

**Settings → Performance → Hardware diagnostics** runs processor, drive, memory and optional connection tests. Nothing runs automatically. The supplied design's drawings and grade animations are connected to native measurements; its random reading generator and fake elapsed timeline are not used. Opening or running Diagnostics does not save settings or display the ordinary unsaved-settings bar. **Optimize downloads**, on the same page, uses sustained calibration and real-download learning; diagnostic grades do not train that tuning.

Results stay in private application data as `diagnostics-latest.json`, replacing the previous report only after a completed run. It includes actual local measurements and a local run identifier for admission/share deduplication. Copy report omits identifiers, paths, endpoint addresses and exact run time/date. A cancelled run keeps the last valid report.

## What is measured

Every throughput sample uses actual processed/received bytes divided by a monotonic `Instant` duration. Three samples produce the median; variation is `(maximum − minimum) / median × 100%`. Samples below one second are marked **short**, so a burst is not presented as stable capacity. Decimal MB/s, GB/s and Mbps are distinct; Mbps ÷ 8 gives MB/s. MiB denotes 1,048,576 bytes.

| Group | Method | Important limits |
| --- | --- | --- |
| Processor | Single-worker SHA-256, zlib level 6 compression, and verified decompression. A deterministic synthetic corpus alternates repeated text and xorshift bytes in 8 KiB regions. It is normally 16 MiB, reduced to a power of two under low memory. Each sample repeats real work until about 500 ms or 32 corpus passes. Digests and compression roundtrips are checked outside algorithm timing. | Compression includes encoder output allocation; decompression includes destination allocation. Data is synthetic and results depend on build/compiler/cache. Fetchrail does not compress or unpack downloads. |
| Drive | Three 64 MiB sequential writes include flush/sync; three reads use the same fixture; three eight-part joins call the actual engine's copy finalization routine and include its `sync_all`. A fixed 1 MiB high-entropy deterministic pattern is generated before timing, repeated and verified byte-for-byte outside write/join timing. Join timing is captured inside the worker, excluding UI sampling waits. | Read results are explicitly OS-cache influenced. This is not an uncached physical SSD test. The ordinary engine often uses shared staging or hardlinks instead of copying all parts, so this join rate is a conditional fallback ceiling. Filesystem compression, caching, sync semantics and other apps affect results. |
| Memory | Three verified buffer-copy samples use `black_box` and compare the destination; three allocation samples use `try_reserve_exact`, initialize/touch every byte and include that work in timing. The available-memory snapshot is refreshed before this group. | Allocation is at most one eighth of observed available headroom and at most 1 GiB; the actual MiB size is shown. Windows takes the minimum of physical, commit/pagefile and virtual headroom from initialized `MEMORYSTATUSEX`. Linux reads `MemAvailable` and visible cgroup v2 headroom. Missing headroom makes allocation unavailable, rather than inventing free memory. Snapshots are volatile; memory/cache performance is synthetic. |
| Connection | Native streamed HTTPS GETs to `speed.cloudflare.com/__down?bytes=…`. HTTP response latency measures time until response headers, including connection/TLS setup when needed. Single and configured-parallel sets use actual aggregate bytes and whole-request wall time. A small real warmup escalates on a fast link; subsequent payloads adapt toward about two seconds using conservative measured whole-request throughput. This avoids inventing bandwidth from a body that was already buffered before the runtime polled it. | Three samples per set, payloads bounded 32 KiB–20 MiB. Requests may share HTTP/2 connections: the label says parallel **requests**, not independent TCP connections. Auto resolves to eight; explicit settings are clamped 1–32. Warmups/latency/failing requests reserve bytes against the same 128 MiB payload cap. Headers/framing/TLS add small network overhead. Slow/offline/truncated/encoded/HTML responses fail honestly. No upload, packet loss, jitter or SDK result-report endpoint is used. |

The network test is a bounded capacity observation and deliberately ignores the app's saved speed cap. This is disclosed before Run. Cloudflare receives the request/IP and may log ordinary provider metadata; Fetchrail sends no measurement result report to the speed-test provider. Disable the checkbox for a completely local run. The protocol follows [Cloudflare's documented download endpoint](https://github.com/cloudflare/speedtest/blob/main/README.md); its JavaScript SDK is deliberately not installed because that SDK also collects completed results.

Relevant API references: [GlobalMemoryStatusEx](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-globalmemorystatusex), [Linux cgroup v2 memory controls](https://docs.kernel.org/admin-guide/cgroup-v2.html), [flate2 ZlibEncoder](https://docs.rs/flate2/1.1.10/flate2/write/struct.ZlibEncoder.html), and [reqwest no-retry policy](https://docs.rs/reqwest/0.13.5/reqwest/retry/fn.never.html). All diagnostic, usage and summary HTTP clients disable automatic retries, redirects, cookies and transfer-context forwarding; TLS verification stays enabled. System proxies are respected in production, while local fixture tests bypass them.

## Budgets, admission and cancellation

The run has a three-minute cooperative time limit. Each network request has a fifteen-second timeout and five-second connection timeout. A single test folder is created exclusively under the chosen download directory, on the filesystem used for downloads. Maximum footprint is 192 MiB and maximum fixture writes are 576 MiB; verification and reads add I/O, not footprint. Files close before the owned folder is removed. Cleanup failure is surfaced rather than reported as successful removal. Files outside that uniquely owned folder are untouched.

Start checks under the engine's dispatch lock. Active transfers, seeders, queued/scheduled jobs and open torrent imports block admission; the user pauses them explicitly. A separate diagnostics-active gate blocks new transfer admissions/mutating torrent operations/organization while measuring and prevents scheduler dispatch. It does not reuse or reset the shutdown/suspend flag. Only one run can be active. Cancelling checks work loops/streams and preserves the last valid result. Shutdown closes admission, cancels the run and sharing, and waits up to fifteen seconds. OS synchronous disk calls cannot safely be interrupted mid-call: a stalled OS, forced termination or hard crash may leave the uniquely named fixture for manual removal. A suspend/time jump may end a run rather than fabricate uninterrupted measurement time.

Native live samples are throttled to roughly 5 Hz, plus step/group boundaries. CPU, memory and drive illustrations show real work progress, not claimed utilization or a physical core inventory. The connection needle and arc share the same measured target on a labelled 0–1,000 Mbps scale; larger readings remain numeric while the drawing saturates. There is no random jitter. Grade badges stay stationary in the live stage, reports and legend. A completed group replaces the live stage with a stable result instead of animating over it; a brief presentation pause is outside measurement timing. Progress is explicitly labelled as the current sample and resets between repeated samples; the report uses sample medians. Reduced motion disables gauge transitions as well. The connection summary shows the best measured download rate, not latency. Reports explain units, which direction is better and sample spread, and retain method details behind an expandable label. Missing measurements retain their reason without fabricated sample statistics.

## Grades and estimates

Version 1 bands are provisional synthetic criteria, stored with each report and defined centrally in native `BANDS`. They are not calibrated rankings of hardware or ISP service. Failed/skipped groups and debug builds are **ungraded**, not grade F or zero. Release builds produce meaningful optimized observations; debug results are engineering diagnostics and cannot be shared as performance bands.

| Representative metric | F | D | C | B | A | S | SS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SHA-256 MB/s | <100 | ≥100 | ≥250 | ≥500 | ≥1,000 | ≥2,000 | ≥4,000 |
| Synced write MB/s | <50 | ≥50 | ≥100 | ≥250 | ≥500 | ≥1,000 | ≥2,000 |
| Memory copy GB/s | <1 | ≥1 | ≥3 | ≥6 | ≥12 | ≥24 | ≥40 |
| Best connection Mbps | <10 | ≥10 | ≥25 | ≥50 | ≥100 | ≥500 | ≥1,000 |

Observed potential is the lower of best measured single/parallel network median ÷ 8 and synced disk-write median. A separate configured ceiling applies the saved global speed limit; this is the report's primary estimated download speed, with the measured potential and cap labelled separately. Local-only runs explain the disabled connection test and show local groups without an unavailable time-estimate table. Per-file caps, sharing that cap among active jobs, server behavior, congestion and test duration can lower real download speed. No CPU/decompression rate is invented as an app bottleneck. Overall uses the provisional band of the measured connection/drive bottleneck, independently of configured bandwidth caps.

For decimal 1, 10 and 60 GB examples, download time is size MB ÷ configured ceiling. Conditional copy time is size MB ÷ measured copy-finalization rate. The displayed range is download-only to download-plus-copy; it never assumes every download needs that copy. There is no unpacking time in totals. Missing successful measurements produce unavailable estimates, with no divide-by-zero fallback. Opt-in summaries, cache effects, short samples and synthetic data cannot support rigorous population capacity estimates.

## Separate per-run sharing permission

The existing usage grant does **not** authorize diagnostic performance fields. A completed release report offers an optional preview, then **Keep local** or **Share this summary**. Native admission requires explicit permission and the current completed run; there is no automatic share, backfill or queue. An attempted share is recorded locally before transport, prevents duplicate/in-flight/restarted sends and is cancellable. Failure never changes diagnostic results or enqueues a retry.

Only app release version, broad OS/architecture and one fixed coarse band counter per successful group may be sent under `purpose: diagnostics-summary-v1`. Example counters: `diagnostics_cpu_b: 1`, `diagnostics_drive_a: 1`. They are aggregated independently; no remote per-run row or ID connects those bands. Exact rates, allocation/available RAM, times, names, paths, models, endpoints, identifiers, error strings and the full report stay local. Native and server allowlists reject arbitrary keys, raw metrics, multiple bands for one group, and diagnostic counters under the ordinary usage purpose.

The recipient is RRMTools' Fetchrail service on Cloudflare. The existing protected aggregate readout, latest thirty UTC calendar-day retention, cleanup alarms and up-to-thirty-day recovery window are reused. Cloudflare sees IPs in transit; our code stores no IP or raw report. Existing logging/tracing exclusions remain. Already combined totals cannot identify a contribution for removal. See [analytics access and retention](analytics.md) and the published privacy policy.

## Checks

`npm run build` and `node scripts/test-diagnostics-ui.mjs @playwright/test` exercise measured gauge targets, no jitter, cancellation, failures/ungraded results, latest reopening, no settings save/bar, conditional estimates, copy exclusions, exact per-run sharing preview/refusal/cancellation, themes/accents/narrow layout and reduced motion. Native diagnostics tests use only temporary local files and controlled local HTTP fixtures for units/medians/roundtrips, bytes/time/concurrency/adaptation, truncation/HTML/encoding/timeout/cancellation, payload budget, safe cleanup and permission/whitelist rules. The release local-only runner test verifies all three local groups and zero public network bytes. Existing usage consent, engine, website and real Workers regression checks remain required. Never run a full public connection benchmark automatically during source checks.
