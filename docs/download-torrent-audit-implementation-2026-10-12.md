## State migration and rollback

Browser request headers survive restart only inside the Windows account-protected
catalog. Linux keeps them in memory and requires fresh browser authorization after
restart; its private checksummed catalog does not persist those headers.

Catalog/settings/queues use `{fetchrail_state: 1, sha256, protected, payload}` envelopes. The checksum covers stored payload bytes and is checked before decryption; no plaintext hash is exposed for protected snapshots. Windows payload is DPAPI ciphertext bound to the Windows account; Linux payload is checksummed base64 in private state files and is **not encrypted**. Existing plain JSON is accepted and rewritten. Only typed valid old generations become `.json.backup`; terminal HTTP publication acknowledges the completed catalog into the backup before removing its journal. Version 1 is introduced by this unreleased change; interim developer fixtures with plaintext-hash envelopes must be recreated, not silently accepted.

Transfer manifests are version 1, contain a typed ETag and `final_url_sha256`, and retain existing range/shared-file layouts for a matching new manifest. Legacy manifests have no trustworthy URL/strength evidence and are not reused. Incompatible attempts are renamed under the private parts directory as `<id>.incompatible-<uuid>`; link replacements use `<id>.previous-source-<uuid>`. They are intentionally retained for recovery, consume disk space, and can be exported/reviewed and explicitly removed after the user no longer needs them. They are never silently merged into the active attempt. Unmarked legacy import directories are preserved rather than guessed to be safe to erase.

Quit Fetchrail before rollback. Older releases cannot read the state envelopes. Under the original Windows account, export each catalog/settings/queues snapshot to a **new file in the same private state folder** using:

```powershell
node scripts/export-state-snapshot.mjs "$env:APPDATA\com.rrmtools.braid\downloads.json" "$env:APPDATA\com.rrmtools.braid\downloads.rollback.json"
```

Repeat for settings and queues, retain the sealed originals, then explicitly replace the older build's three JSON files with the corresponding exported plain JSON. These exports can contain credentials and must stay private. Prefer restoring the old build's own valid pre-upgrade backups if available. Old date-based resume logic remains unsafe; do not feed quarantined attempts back into it without independent integrity verification. Rollback does not delete payload files or publish a release.

## Verification record

Verification is Windows local/loopback unless stated otherwise. No WAN throughput improvement, HDD gain, Linux desktop parity, power-loss durability or packet isolation is claimed. Existing `.github/release.yml` already groups the `bug`/`fix` label category and remains unchanged.

- `cargo test --manifest-path src-tauri/Cargo.toml --lib --locked torrent::audit_tests`: **2 passed**, including native denied-replacement/old-resume preservation, retry, tracker durability and missing-resume recreation.
- `cargo test --manifest-path src-tauri/Cargo.toml --lib --locked state_store::tests`: **2 passed**, including ciphertext checksum/nonexposure of the plaintext digest, pre-decrypt corruption rejection and validated backup preservation.

- `npm.cmd run torrent:ui`: **passed** with 1,000 records, 10,000 files, 2,000 peers and 4 Hz updates for 15 seconds; action-to-paint p95 **16.1 ms**, no recorded steady-state stalls or JavaScript errors. This is a frontend fixture, not engine history-save/WAN throughput evidence.
- `node scripts/test-state-snapshot.mjs`: **passed** after the final checksum change: 10,000-row DPAPI snapshot through stdin, damaged checksum/payload rejected, no Windows environment-variable payload limit.
